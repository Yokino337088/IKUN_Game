## 一、这个 Bug 到底有多坑？

今天遇到的 Bug 其实是**两个坑叠在一起**：

### 第一个坑：状态切换不出来
按 J 攻击 → 攻击动画做完了 → 角色**永远停在待机动画不动了**，按什么都没反应。

### 第二个坑：攻击完永远在循环攻击动画
按 J 攻击 → 攻击动画循环播放了 13 次（用户截图实锤）→ 就是不切回待机。

---

## 二、排查历程：从"动画卡死"到"找到真凶"

### 阶段1：最初的Bug描述

用户最开始说的问题是：
> "不对，但你这样改了之后玩家初始化之后的动画就会一直停留在待机动画的状态，之后就切换不了其他的动画状态了啊"

然后用户发了一张Animancer窗口的截图，显示：
- 普攻动画已经循环了 **13次**（`6.55181 x13`）
- 待机状态的 Weight 是 0.0（不在播放）
- 普攻状态的 Weight 是 1.0（正在播放）
- 动画没有停止，一直循环

---

### 阶段2：一开始以为是"Animancer死锁"

**第一反应**：看到"动画卡死"四个字，立刻想到了之前记录的那个"同步事件级联导致状态机重入"的Bug。觉得这就是同样的问题。

**猜测的根因**：
```
按J攻击 → 进入普攻状态 → 播放攻击动画
    ↓
攻击动画播到85% → AttackComplete回调触发
    ↓
ChangeState(待机) → 待机状态.EnterState()
    ↓
注册输入事件监听的同时，如果有输入事件同步触发
    ↓
状态机重入，animancer.Play()被同一帧多次调用
    ↓
Animancer内部状态混乱，动画冻结
```

**排查方向**：去检查事件回调里有没有添加防重入保护，看看`ChangeState`有没有被加了帧级锁。

**验证方法**：查看`BossPlayerAttackState.cs`里的`AttackComplete`回调，检查`_isCompleted`防重入标志。

---

### 阶段3：发现不对劲

检查了代码：
```csharp
private void AttackComplete()
{
    if (_isCompleted)  // ← 有防重入保护！
        return;

    _isCompleted = true;
    AIObj.LaunchBullet();
    ChangeState(E_BossPlayerStateType.待机);
}
```

**问题来了**：明明有防重入保护，为什么动画还在循环13次？

再仔细看截图：`6.55181 x13` → 这说明**AttackComplete回调根本没被触发**！如果有被触发，动画早就切换到待机了，不会在普攻状态循环13次！

**顿悟**：这不是"Animancer死锁"的问题，而是**动画事件根本没触发**！

---

### 阶段4：追查动画事件为什么不触发

去查看`AddAnimationEvent`方法的实现：

```csharp
// BossPlayerState.cs
protected void AddAnimationEvent(float normalizedTime, Action callback)
{
    if (_currentAnimState == null)
    {
        LogSystem.Debug("状态为空，不能添加动画事件");
        return;
    }

    // 获取事件序列
    _currentEventSequence = _currentAnimState.Events;  // ← 这里错了！
    
    _currentEventSequence.Clear();
    _currentEventSequence.Add(normalizedTime, callback);
}
```

**找到根因了**！`_currentAnimState.Events` — 我一直以为`Events`是一个**属性**，但实际上它是Animancer的一个**方法**！

正确写法应该是：
```csharp
_currentAnimState.Events(AIObj, out _currentEventSequence);
```

**错误原因**：
- `Events`是方法，需要传入owner对象和out参数
- 直接调用`.Events`会报错，或者返回一个无效的引用
- 事件根本没有被正确注册，所以`AttackComplete`永远不会被调用

---

### 阶段5：还有另一个问题 - 冷却时间缺失

修复了`Events`调用后，用户提到"攻击时狂按移动键"还是会出问题。

这时候意识到，虽然动画事件现在能触发了，但**没有冷却时间机制**：
- 玩家可以疯狂按J，攻击状态刚切到待机，J键又被按下，立刻切回攻击
- 动画事件触发的同时，输入事件也在触发，可能造成混乱

**解决方案**：加上冷却时间：
- 进入普攻状态时：`_attackCooldownTimer = attackCooldown`
- 在`OnAttackPressed`里检查：`if (!CanAttack()) return;`
- `Update`里每帧减少计时器

---

### 阶段6：加双保险

考虑到Animancer的动画事件系统可能还有其他不确定性（比如fadeDuration期间的过渡状态），决定再加一个**备用方案**：

```csharp
public override void UpdateState()
{
    base.UpdateState();
    
    // 双保险：如果动画事件没触发，用Update检测进度
    if (!_isCompleted && _currentAnimState != null)
    {
        float normalizedTime = _currentAnimState.NormalizedTime % 1;
        if (normalizedTime >= 0.85f && normalizedTime < 0.9f)
        {
            AttackComplete();
        }
    }
}
```

---

### 最终结论：原来有两个独立的Bug

| Bug | 现象 | 根因 | 修复 |
|-----|------|------|------|
| Bug 1 | 状态切换不出来 | `_canReceiveInput`依赖`UpdateState()`调用，但BossPlayerControl没调用 | 改用`_stateEnteredFrame`帧号判断 |
| Bug 2 | 动画事件不触发 | `Events`是方法不是属性，调用方式错误 | 改用`Events(AIObj, out seq)` |

## 三、修复历程（详细步骤）

### 第1步：发现第一个问题 - 状态切换不出来

**现象**：修改代码后，玩家初始化后就一直是待机，按什么键都切换不了状态。

**排查**：看了代码，发现之前用的是 `_canReceiveInput` 这个变量：

```csharp
// BossPlayerState.cs 旧代码
protected bool _canReceiveInput;

public override void EnterState()
{
    _canReceiveInput = false;  // 进入状态时，不让接收输入
    // ...
}

public override void UpdateState()
{
    _canReceiveInput = true;   // 到下一帧 Update，才允许接收输入
}
```

**问题根源**：状态机的 `UpdateState()` 根本没被调用！

看 [BossPlayerControl.cs](file:///d:/Unity_Project/IKUN_Game/Assets/Scripts/游戏逻辑/4第四章_黄昏/boss战_2/玩家控制/BossPlayerControl.cs#L126) 的 Update 方法：

```csharp
void Update()
{
    FlipPlayer();
    PlayerMove();
    stateMachine.UpdateState();  // ← 这个是后来才加上的！之前没有！
}
```

**结果**：`_canReceiveInput` 永远是 `false`，所有输入事件都被忽略了，状态当然切换不了！

**修复方案**：别用 `_canReceiveInput` 了，改用记录**帧号**的方式：

```csharp
// BossPlayerState.cs 修复后
public override void EnterState()
{
    _stateEnteredFrame = Time.frameCount;  // 记录进入状态的这一帧
    // ...
}

// 然后在事件回调里判断
private void OnAttackInput()
{
    // 如果当前帧就是进入状态的那一帧，就忽略
    if (Time.frameCount == _stateEnteredFrame) 
        return;
    
    ChangeState(E_BossPlayerStateType.普攻);
}
```

这样就**不需要 UpdateState() 的调用**了，直接比较帧号就行！

### 第2步：发现第二个问题 - 动画事件根本没触发

**现象**：普攻动画循环播放了13次（用户截图里的 Animancer 窗口显示 `6.55181 x13`），就是不触发 `AttackComplete` 回调。

**排查**：问题出在 [BossPlayerState.cs](file:///d:/Unity_Project/IKUN_Game/Assets/Scripts/游戏逻辑/4第四章_黄昏/boss战_2/玩家控制/玩家状态机/base/BossPlayerState.cs) 的 `AddAnimationEvent` 方法里！

```csharp
// 旧代码 - 完全错了！
_currentEventSequence = _currentAnimState.Events;  // ← Events 根本不是属性！
_currentEventSequence.Clear();
_currentEventSequence.Add(0.85f, AttackComplete);
```

**真相**：`AnimancerState.Events` 是**一个方法**，不是属性！正确的调用方式是：

```csharp
// 正确调用
_currentAnimState.Events(AIObj, out _currentEventSequence);
```

而且之前的代码还犯了一个错误：把事件序列保存到列表里，但根本没正确使用！

**修复方案**：重写 `AddAnimationEvent` 和 `ClearAnimationEvents` 方法：

```csharp
protected void AddAnimationEvent(float normalizedTime, Action callback)
{
    if (_currentAnimState == null)
        return;

    // 正确获取事件序列
    _currentAnimState.Events(AIObj, out _currentEventSequence);
    
    _currentEventSequence.Clear();
    _currentEventSequence.Add(normalizedTime, callback);
}

protected void ClearAnimationEvents()
{
    if (_currentEventSequence != null)
    {
        _currentEventSequence.Clear();
        _currentEventSequence = null;
    }
    
    if (_currentAnimState != null)
    {
        AnimancerEvent.Sequence events;
        _currentAnimState.Events(AIObj, out events);
        events.Clear();
    }
}
```

### 第3步：加个双保险 - Update 里手动检测

考虑到 Animancer 动画事件可能还是不靠谱（毕竟之前踩过坑），我们加一个**备用方案**：

在 `UpdateState()` 里**自己检测动画播放进度**，如果到了 85% 就手动触发回调！

```csharp
// BossPlayerAttackState.cs
public override void UpdateState()
{
    base.UpdateState();
    
    // 备用方案：如果动画事件没触发，用这个兜底
    if (!_isCompleted && _currentAnimState != null)
    {
        float normalizedTime = _currentAnimState.NormalizedTime % 1;
        if (normalizedTime >= 0.85f && normalizedTime < 0.9f)
        {
            AttackComplete();
        }
    }
}
```

技能和大招状态也一样加上这个兜底逻辑！

### 第4步：锦上添花 - 加冷却时间

防止玩家狂按同一个键导致重复触发，加个冷却时间：

1. 在 [BossPlayerControl.cs](file:///d:/Unity_Project/IKUN_Game/Assets/Scripts/游戏逻辑/4第四章_黄昏/boss战_2/玩家控制/BossPlayerControl.cs) 加字段：

```csharp
[Header("普攻冷却时间（秒）")]
public float attackCooldown = 0.5f;

private float _attackCooldownTimer;
```

2. 在 Update 里更新计时器：

```csharp
void Update()
{
    // ...
    UpdateCooldowns();
}

private void UpdateCooldowns()
{
    if (_attackCooldownTimer > 0)
        _attackCooldownTimer -= Time.deltaTime;
}
```

3. 在输入事件里检查冷却：

```csharp
private void OnAttackPressed()
{
    if (Time.frameCount == _lastActionEventFrame) 
        return;
    
    // 冷却时间检查
    if (!CanAttack()) 
        return;
    
    _lastActionEventFrame = Time.frameCount;
    EventCenter.Instance.EventTrigger(MyEventTypeString.玩家普攻事件);
}
```

4. 在状态进入时开始计时：

```csharp
public override void EnterState()
{
    base.EnterState();
    _isCompleted = false;
    AIObj.StartAttackCooldown();  // ← 开始冷却
    PlayAnimation(E_BossPlayerStateType.普攻);
    AddAnimationEvent(0.85f, AttackComplete);
}
```

## 六、为什么一开始排查方向跑偏了？

### 当时的错误思路

用户说的是："不对，但你这样改了之后**玩家初始化之后的动画就会一直停留在待机动画的状态**，之后**就切换不了其他的动画状态**了啊"

但我一看"动画卡死"四个字，脑子里就想到了之前写的那个"同步事件级联导致状态机重入"的术语，觉得这就是根因，开始往事件级联方向排查。

### 问题在哪？

| 错误想法 | 正确想法 |
|----------|----------|
| "动画卡死" = "事件级联" | "动画卡死"可能有100种原因，要先验证是哪种 |
| "术语听起来很专业" | 专业术语可能是之前别的bug的根因，不是这次的问题 |
| "直接分析代码逻辑" | 应该**先加日志**，确认代码执行到哪一步了，比空想有效100倍 |

### 正确的排查顺序

```
用户说"初始化后切换不了状态"
    ↓
step 1：加日志确认"状态切换代码有没有被执行"
    ↓
如果执行了 → 排查动画系统（Animancer配置？）
如果没执行 → 排查输入事件有没有收到
    ↓
step 2：加日志确认"UpdateState有没有被调用"
    ↓
如果没调用 → 找到了！BossPlayerControl.Update里没调用！
```

## 七、最终吸取的教训

| 教训 | 说明 |
|------|------|
| **先确认现象，再找原因** | 用户说"切换不了"就先验证"状态切换代码有没有被执行"，别急着下结论 |
| **不要被专业术语带跑** | "同步事件级联"听起来很专业，但它不是这次bug的根因 |
| **从最简单的地方开始排查** | 加几行日志，看看代码执行到哪一步了，比空想有效100倍 |
| **看清楚用户的描述** | 用户说"初始化之后就有问题"，这就是关键线索，不是"后来卡死的" |
| **API 文档要仔细看** | 不能想当然地觉得 `Events` 是属性，实际上它是个方法！ |
| **不要依赖单一机制** | 动画事件可能不靠谱，加个 Update 检测的双保险更好 |
| **冷却时间很重要** | 防止玩家狂按按键造成各种奇怪问题 |
| **能用简单方案就别用复杂的** | 用帧号判断比用 `_canReceiveInput` 依赖 Update 调用简单多了 |
